## 配置数据

配置入口在 HKCU 的 `Software\Stardock\Fences` 下。已确认 `Settings.GetKey` 通过当前用户注册表打开相应子键。`tools/reverse/export_config.py` 只读导出了本机 5 个分组、12 条规则和 39 个图标记录，分组字段解析没有报错。原始配置仅保存在本机 `research/evidence/fences-config.json`，不会在报告里展开用户的文件路径。

### 分组

`Groups` 子键的默认值记录数量，数字名称的值保存以 `|` 分隔的记录。反编译 `DeskGroupSettings.Reload` 和 `DeskGroup.ToString` 可交叉核对以下 23 个字段：

| 序号 | 字段 | 用途 |
|---|---|---|
| 0 | ID | 图标与规则引用的分组 ID |
| 1–4 | x, y, cx, cy | 位置和尺寸 |
| 5 | scroll | 滚动状态 |
| 6–7 | title, monitor name | 名称、显示器标识 |
| 8–11 | MonitorX/Y/CX/CY | 显示器坐标及大小 |
| 12–13 | SortMethod / SortFlags | 排序方法和标志；具体枚举尚未完全确认 |
| 14 | Opacity | 透明度参数；范围与映射待核对 |
| 15 | SwipeIndex | 桌面页面索引 |
| 16 | szFolder | 文件夹映射路径；非空即 IsFolderView |
| 17–18 | Edge / EdgeLast | 边缘停靠状态 |
| 19–20 | Rolledup / RolledupDockedLast | 折叠和上次停靠折叠状态 |
| 21 | dwViewFlags | 视图标志；位定义待核对 |
| 22 | GUID | 分组稳定标识 |

标题、显示器名和文件夹等字符串使用反引号编码空格；文件夹路径读取时支持环境变量展开。兼容导入需要处理旧版本字段不足，不能假定记录总有 23 个字段。

证据：`decompiled/managed/DesktopDockUI.Simulation.DeskGroupSettings.type.txt` 与 `DesktopDockUI.Simulation.DeskGroup.type.txt`。

### 图标

`Icons` 子键以文件路径为值名，数据同样由 `|` 分隔。基础字段包含分组 ID、绝对位置、相对位置、是否使用绝对位置；扩展字段包含显示器关联、打开次数、加入分组时间、关联程序、页面索引和最近点击时间。

这说明完善的独立产品应分别保存“文件身份 / 图标归属 / 布局坐标”，而不必为视觉分组移动真实文件。该设计建议来自配置结构；具体原程序拖拽和文件操作行为仍需进一步确认。

证据：`decompiled/managed/DesktopDockUI.Simulation.IconElementSettings.type.txt`。

### 规则

`RuleSettings.Reload` 最多读取 50 条，键名为 `00` 至 `49`，每条搭配 `<序号>_Target`。当临时强制语言开启时，规则子键名可变为 `Rules-<语言>`。本次导出使用常规 `Rules` 子键。

目标记录包含 Enabled、TargetGroupID、PlaceAtEndOfTargetGroup 和 AutoGeneratedID。规则本身包含名称及多个 Criteria。`Criteria` 的参数包含方法名、操作符、整数参数、字符串参数，以及表示新 OR 条件组的 `StartOfNewGroup_Or`。这证明条件组合模型存在；原生执行端的完整 AND/OR 求值顺序仍待核对。

已有条件类覆盖类型、名称、程序、目标、修改时间、大小、时段、星期和打开次数。因此当前原型只有扩展名与名称包含规则，距离原版规则范围仍有缺口。

证据：`RuleSettings.cs`、`Rule.cs`、`DesktopDockUI.Simulation.Criteria.type.txt` 和 `DesktopDockUI.Simulation.type.txt`，位于 `decompiled/managed`。

## 布局与快照

`.fencelayout` 模板由 .NET `XmlSerializer` 序列化。Layout / LayoutArea 模型使用相对宽高、对齐方向、类别偏置、间距和有舍入 / 无舍入的尺寸与偏移修正。

快照创建写入同 GUID 的 `.xml`、`.png` 和 `_thumb.png`；XML 数据涵盖 Groups、Icons、Settings、ViewStates、NavHistory、Skinning。恢复路径写回这些分支并触发桌面完整重载、分辨率相关更新。截图请求通过窗口消息发送给原生侧。我们只反编译这些方法，未执行创建、恢复、消息发送或写入原程序注册表。

证据：`DesktopDockUI.Helpers.ObjectSerializer.type.txt`、`DesktopDockUI.Layouts.LayoutArea.cs`、`DesktopDockUI.Dialogs.Panes.ToolsPaneA.TakeSnapshot.txt`、`DesktopDockUI.Dialogs.Panes.ToolsPaneA.RestoreSnapshotBasic.txt`。

## 原生桌面集成

1. `FindDesktopWindowSlow`（地址 `18006e010`）先找 `Progman → ShellDLL_DefView → SysListView32`，再尝试 NDesk；仍找不到时枚举顶层窗口。
2. 枚举回调（`180053ca0`）检查 WorkerW 是否拥有 DefView 和桌面 ListView。由此已确认支持 WorkerW 桌面承载结构，超出了仅搜索 Progman 的简化实现。
3. `ForceLoad`（`18006df50`）沿调用路径找到 `Shell_TrayWnd`，获取其进程 ID，并进入后续加载函数。导出名及字符串不足以说明具体装载方法，后续函数还需分析。
4. `OnProcessAttach`（`18006ea70`）创建初始化线程。该线程注册 `DesktopDockDllMain` 窗口类，并创建隐藏窗口运行消息循环。
5. 托管侧通过 Progman 的 `hwndListView` 属性取得桌面 ListView；重载通过窗口属性计数和重绘通知。原生初始化如何维护这些属性仍须沿调用链确认。
6. `Shell_GetLnkPath` 包含 MSI 快捷方式查询，以及 COM 加载与路径 / 参数读取。独立实现应覆盖 MSI advertised shortcut，不能只把 `.lnk` 当成普通文本路径。
7. `GetResolutionFingerprint` 以显示器信息组成指纹字符串，可作为多显示器与分辨率变更布局的调查入口；部分参数类型仍是反编译推断。
8. FencesMenu64 的 `DllGetClassObject` 和 `DllRegisterServer` 已反编译；日志与调用链确认该模块包含 DesktopDock_ContextMenu 的 COM 工厂与注册入口。完整菜单项构建和命令分发尚未分析。

证据：`decompiled/native` 下的 `.json` 是原始 MCP 响应，`.c` 是抽出的伪代码。该阶段未注入 Explorer、未加载 Fences DLL 执行、未改动 Windows 桌面窗口。
